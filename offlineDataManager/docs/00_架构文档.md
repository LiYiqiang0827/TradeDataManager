# 00 架构文档

> 本文基于 **2026-09-15 修复版**代码,描述 offlineDataManager 的整体架构。读完后应能理解:**数据从哪来 → 怎么存 → 怎么读 → 谁在调度**。

---

## 1. 项目定位

offlineDataManager 是 A 股金融数据的**离线下载与本地化层**,运行在用户本地 macOS 上。

- **输入**:Tushare pro API + 开盘啦 HTTP API
- **输出**:4 个 SQLite 数据库(按主题分库,basic / kpl / news / index)
- **消费者**:上层在线服务(onlineDataManager)、策略脚本、AI Agent 的查询调用

它不直接服务 HTTP / WebSocket 请求,**只负责把数据搬到本地并提供只读接口**。所有实时性由 onlineDataManager 处理。

**关键边界**:
- **Layer 0/0.5 跟 Layer 1/2/3 完全是不同进程**。Service 子进程有自己的 `CNDataDown` 实例,自己开 SQLite 连接,自己写日志
- **Layer 2 和 Layer 3 共用 `core/offline_db_client.py` 的工具**(init_db / upsert / replace / get_conn),但 Layer 2 走 `CNDataDown` 的方法,Layer 3 走 `get_*` 函数,代码路径完全独立

## 3. 数据流:一条数据从 Tushare 到消费者手里

以"今天的日 K 行"为例:

```
1. launchd 启动 scheduler
   ~/Library/LaunchAgents/com.tradingagent.scheduler.offlineData.plist
   → /opt/anaconda3/bin/python3 -m scheduler.scheduler_updateData --daemon

2. 时间到 09:05,schedule 触发 task_morning_update(快速补:涨跌停价 + kpl 涨停榜 + 联播新闻)

3. task_full_update 按 4 阶段同步 spawn service:
   第 2 阶段: spawn_service("service_daily", ["--trade-date", "20260915"], sync=True)
     ↓ subprocess.run
   service_daily 启动:
     - 解析 args
     - 调 resolve_date_range(conn_basic, "cn_daily", args) → (sd, ed, desc)
     - 实例化 down = CNDataDown()(开 3 个 DB conn)
     - 调 down.update_daily(start_date=sd, end_date=ed)
         ↓
       CNDataDown.update_daily:
         - 读 ctrl_basic("cn_daily") 拿上次最大日期
         - 按日期循环 cur=sd..ed
           - self.client.daily(trade_date=td, limit=6000, offset=offset)
             ↓
             TushareClient.daily → tushare pro.daily HTTP 调用
             返回当日所有股票 OHLCV 的 DataFrame
           - df["snap_ts"] = snap_ts()
           - upsert_df(conn_basic, df, "tbl_cn_day", key_cols=["ts_code","trade_date"])
             ↓
             INSERT OR IGNORE 写入 db_cn_basic.db
           - 推进 ctrl_basic("cn_daily") = td
     - 返回 inserted 行数,service 进程退出 rc=0
     ↓
   subprocess.run 收 rc=0,scheduler 继续下一个 service

4. 数据已落地 db_cn_basic.db:tbl_cn_day
   消费者通过 get_day(ts_code='600000.SH', trade_date='20260915', qfq=True) 读:
     - get_day 内部:
       - SELECT * FROM tbl_cn_day WHERE ts_code=? AND trade_date=?
       - JOIN tbl_cn_adj_factor 计算前复权
         qfq_factor = adj_factor[当天] / adj_factor[最新]
         price_qfq = raw_price * qfq_factor
         vol_qfq   = raw_vol   / qfq_factor
       - 返回前复权 DataFrame

整条链路单日从拉取到消费者可读,延迟 = service 跑完的时间(几十秒级)
```

## 4. 数据库分库策略

**4 个 SQLite 库,按主题分**(2026-09-15 加 index):

| DB | 主题 | 大小 | 写入者 | 读取者 |
|---|---|---|---|---|
| `db_cn_basic.db` | 基础数据(基本面 / 日 K / 复权 / 周月 K / 交易历) | 3.6 GB | `CNDataDown.update_basic/update_daily/update_adj_factor/update_tradecal/update_week/update_month` | `get_day / get_week / get_month / get_tradecal / get_basic / get_adj_factor / get_ctrl_basic` |
| `db_cn_kpl.db` | 开盘啦(涨停榜 / 题材 / 涨停表现) | 1.1 GB | `update_kpl_list / update_kpl_concept_cons / update_kpl_limit_performance` | `get_kpl_list / get_kpl_concept_cons / get_kpl_limit_performance` |
| `db_cn_news.db` | 新闻(快讯 / 长新闻 / 联播) | 6.4 GB | `update_news / update_major_news / update_cctv_news` | `get_news / get_major_news / get_cctv_news / get_news_ctrl` |

**分库好处**:
- 备份策略独立(可以只备份 basic,kpl/news 重建容易)
- 锁竞争隔离(basic 写入时 news 只读)
- **大库分摊**(6.4 GB 的 news 单独一个文件,操作时不会触碰 basic)

**统一断点表**(2026-09-15 重构,**每个 DB 一个本地 ctrl 表**):
- 4 个数据库各有自己的 ctrl 表
- **断点表跟数据表在同一个 DB**(每张表的断点存在数据所在 DB 里)
  - `db_cn_basic.db:tbl_basic_ctrl` ← 12 个 key(cn_basic / cn_daily / cn_adj_factor / cn_tradecal_SSE / cn_tradecal_SZSE / cn_stk_limit / cn_suspend / cn_moneyflow / cn_margin / cn_margin_detail / cn_cyq_perf / cn_daily_basic)
  - `db_cn_kpl.db:tbl_kpl_ctrl` ← 9 个 key(cn_kpl_list / cn_kpl_concept_cons / cn_kpl_limit_performance / cn_top_list / cn_top_inst / cn_block_trade / cn_ggt_daily / cn_hsgt_top10 / cn_limit_list),2026-09-15 重建
  - `db_cn_index.db:tbl_index_ctrl` ← 2 个 key(cn_index_basic / cn_index_daily),2026-09-15 新建
  - `db_cn_news.db:tbl_news_ctrl` ← 11 行(9 个 news 源 + cctv_news + major_news)

## 5. 调度层:scheduler + service 子进程

### 5.1 scheduler 进程

`scheduler/scheduler_updateData.py` 启动方式:
- launchd plist `KeepAlive=True` 拉起 `python3 -m scheduler.scheduler_updateData --daemon`
- 或手动跑 `--full` / `--once service_xxx` / `--status`

scheduler 做的事:
1. **启动时立即跑一次 `task_full_update`**(保证新启动后数据是新的)
   - **注意**:不管断点是否刚推进过,都重跑完整 4 阶段。如果 launchd 重启或 `--daemon` 重新拉起,会浪费一次 API 配额(主键去重保证幂等,但仍会拉取)
   - **如果想避免**:手动启动 `--daemon` 前先观察 cron 刚跑过不久就别重启
2. **挂起主循环**:`while True: schedule.run_pending(); time.sleep(30)`,每 30 秒检查一次

### 5.2 调度时间表

| 时间 | 任务 | 子进程 |
|---|---|---|
| 09:05 | `task_morning_update` | 快速补:`service_stk_limit` + `service_kpl_list` + `service_cctv_news`(用户开盘前用) |
| 16:30 / 20:00 | `task_kpl_limit_performance` | 增量(实时补 kpl_list 滞后) |
| 18:00 / 20:00 / 22:00 | `task_full_update` | 4 阶段全量(收盘后兜底) |
| 每 10 分钟(08:00 - 次日 05:00) | `task_news_update` | 增量(异步,不阻塞) |

**`task_full_update` 4 阶段**:
1. 基础数据:`service_basic` → `service_tradecal`(任一失败整体 return)
2. 日 K 链:`service_daily` → `service_adj_factor`(任一失败整体 return)
3. 周月 K:`service_week` → `service_month`(任一失败整体 return,内部 rc=2 区分"业务中止"vs"异常")
4. kpl + 涨跌停 + 龙虎榜 + 大宗 + 港股通 + 沪深股通 + 涨跌停列表 + 资金流向 + cctv:`service_kpl_list` → `service_kpl_concept_cons` → `service_kpl_limit_performance` → `service_stk_limit` → `service_suspend` → `service_top_list` → `service_top_inst` → `service_block_trade` → `service_ggt_daily` → `service_hsgt_top10` → `service_limit_list` → `service_moneyflow` → `service_cctv_news`(任一失败只 logger.error,继续下一项)

### 5.3 service 子进程

每个 service 是一个**独立 Python 进程**,通过 `python3 -m service.xxx` 启动。spawn 由 `spawn_service(extra_args, sync)` 实现:
- `sync=True`:`subprocess.run` 阻塞,等子进程退出(用于全量更新链路)
- `sync=False`:`subprocess.Popen` 后台,不等返回(用于 news 高频更新)
- `PYTHONPATH` 在 env 里加 `~/TradingAgent/`,这样 service 能 `import coreClient.tushare_client`
- `cwd = scripts/`,这样 `service.xxx` 包能找到
- 子进程的 stdout/stderr 重定向到 `logs/service_*.log`(20-50 MB 自动 rotate)
- 30 分钟超时

**子进程返回值**:
- `rc=0`:成功
- `rc=1`:Python 异常退出
- `rc=2`:**业务中止**(目前仅 `service_week` / `service_month` 在 ctrl 一致性校验失败时返回)
- `rc != 0 && abort_on_failure=True`:`spawn_service` 抛 `RuntimeError`,scheduler 决定是否中止后续

### 5.4 依赖链

```
basic / tradecal          (无依赖,可任意顺序)
        ↓
    daily → adj_factor    (按日期循环拉,必须按顺序)
        ↓
   week / month           (强校验:ctrl.cn_daily == ctrl.cn_adj_factor == today)
                         (失败返回 rc=2 业务中止,scheduler 不再继续)
        ↓
kpl_list / kpl_concept / kpl_limit_perf / cctv_news  (互相独立,任一失败不阻断其他)
```

### 5.5 一次性测试调度(scheduler_once)

`scheduler/scheduler_once.py` 是 2026-09-16 新增的**一次性测试调度**(配合常驻 scheduler_updateData)。

**对比**:

| 维度 | scheduler_updateData | scheduler_once |
|---|---|---|
| 运行方式 | launchd 常驻 + schedule 定时 | **一次性,跑完即退出** |
| 任务选择 | 按时间窗口选 task | **按依赖顺序跑全部/指定** |
| 用途 | 生产环境定时更新 | **首次回填 / 测试 / 批量补跑** |
| 跳过逻辑 | 不跳过 | 支持 `--only` / `--skip` |

**依赖编排**(6 个阶段,27 个 service):

```
阶段 0: 元数据
  service_tradecal / service_basic / service_index_basic
阶段 1: K 线
  service_daily / service_adj_factor / service_week / service_month
阶段 2: 衍生数据
  service_daily_basic / service_moneyflow / service_stk_limit / service_suspend / service_index_daily
阶段 3: KPL
  service_kpl_list / service_kpl_concept_cons / service_kpl_limit_performance
阶段 4: 高级数据
  service_top_list / service_top_inst / service_block_trade / service_ggt_daily
  service_hsgt_top10 / service_limit_list / service_margin / service_margin_detail / service_cyq_perf
阶段 5: 新闻
  service_news / service_major_news / service_cctv_news
```

**CLI 用法**(`--only` 灵活度高,2026-09-16 增强):
- `--only stage0`:只跑阶段 0
- `--only kpl_list`:只跑 1 个 service
- `--only kpl_list daily_basic index_daily`:跑多个(空格分隔)
- `--only kpl_list,daily_basic,index_daily`:跑多个(逗号分隔)
- `--only stage0 stage3`:跑多个阶段
- `--skip cctv_news`:跳过某些
- `--continue`:任一失败不中止,继续跑
- `--dry-run`:只打印计划

## 6. 多 service 多进程:为什么这么设计

参考 MyATM `database_scheduler.py` 的模式。每个 service 独立的好处:

1. **隔离性**:一个 service 崩了不影响其他(launchd 重启整个 scheduler 即可)
2. **可观测性**:每个 service 自己一个 log 文件,问题定位快
3. **可单独调用**:`--once service_daily` 单独跑一个,不需要启动全套
4. **资源峰值分摊**:完整更新链路 4 阶段,日 K / 复权 / 周月 K 都是按日期循环,内存峰值在 service 内部
5. **断点独立**:每个 service 走自己的 ctrl,失败重跑只重跑没成功的部分

代价:
- 子进程 spawn 有 ~0.5s 开销(可接受)
- 每个 service 都要 import pandas / tushare,启动慢 ~2s(可接受)

## 8. 关键设计原则(已落地,不要再改)

1. **日 K 存不复权原始数据**(`tbl_cn_day`)。前复权只在 `get_day(qfq=True)` 读时 join `tbl_cn_adj_factor` 计算
   - 原因:原始数据可追溯,任意时刻都能根据 adj_factor 重算前复权
   - 副产物:周月 K 派生表里直接是前复权,没有"周月 K 不复权"模式

2. **周月 K 是派生表**(`tbl_cn_week` / `tbl_cn_month`),从 `tbl_cn_day` × `tbl_cn_adj_factor` 聚合,**覆盖更新**(DELETE 全表后 INSERT,事务化见 `replace_table`)
   - 原因:周月 K 计算结果依赖日 K 的最新状态,不能增量追加(会出逻辑错误)
   - 写入完成后整个表的内容是确定的、可重算的

3. **依赖链严格顺序**:`daily → adj_factor → week → month`
   - `service_week` / `service_month` 启动时校验 `ctrl.cn_daily == ctrl.cn_adj_factor == today`
   - 不一致就 rc=2 业务中止(不会用过期数据算出错的周月 K)

4. **4 个数据库连接,各自独立**(`CNDataDown` 持有 `conn_basic` / `conn_kpl` / `conn_news` / `conn_index`)
   - 避免跨库事务(本来 SQLite 也不支持)
   - 写入失败影响范围最小

5. **断点表跟数据表在同一个 DB**:
   - basic 数据 / basic ctrl 同 DB
   - news 数据 / news ctrl 同 DB
   - kpl 数据 → 实际写到 basic ctrl(历史原因,2026-09-15 修复版统一)

6. **`replace_table` 必须事务化**:DELETE + INSERT 在一个 BEGIN/COMMIT 里,中途崩了不会丢表(2026-09-15 修复)

7. **kpl 双源补 T+1 滞后**:
   - `tbl_cn_kpl_list` 来源 tushare `pro.kpl_list`,第二天早上更新
   - `tbl_cn_kpl_limit_performance` 来源 kpl API `DailyLimitPerformance`,16:30 后实时
   - 两表互补,同一天的同一只股可能在两表都有(读时按场景选表)
