# 修改记录

按**被修改的文档**归档重大变更。每个被改过的文档都有自己的 changelog,记录该文档的所有历史改动。

## 设计原则

**per-文档 changelog**(不是 per-事件):每个文档的修改历史集中在一份文件里,容易追溯"这个文档经历了哪些大改动"。

## 文件命名约定

**`changelog_<原文档相对路径>.md`**

其中 `<原文档相对路径>` 是该文档在 `~/LLM Wiki/TradingAgent/offlineDataManager/` 下的相对路径,**去掉 `.md` 扩展名,保留目录层级**(用 `_` 分隔)。

例:
| 原始文档路径 | changelog 文件名 |
|---|---|
| `README.md` | `changelog_README.md` |
| `01_数据详细设计文档.md` | `changelog_01_数据详细设计文档.md` |
| `代码详细设计/offline_downloader.md` | `changelog_代码详细设计_offline_downloader.md` |
| `代码详细设计/service_cyq_perf.md` | `changelog_代码详细设计_service_cyq_perf.md` |

**说明**:
- `代码详细设计/` 改成 `_`(下划线),避免 `/` 在文件名里
- 中文文件名是允许的(macOS/Linux 都能处理)

## 何时新建 changelog

**每次修改以下任何一个文档,且改动是"重大变更"时**,在 `修改记录/` 下新建或更新对应的 `changelog_*.md`:

| 文档类型 | 是否需要 changelog |
|---|---|
| 顶层文档(README/00/01/02/03/QuickStart) | **需要** |
| 代码详细设计/*.md | **需要** |
| 修改记录/README.md | 不需要(本身是目录说明) |
| 评估报告/README.md | 不需要(本身是目录说明) |

**"重大变更"判定标准**:
- ✓ 加新表/新字段/新接口
- ✓ 修真实 bug
- ✓ 重构(模块拆分、命名变更)
- ✓ 重大数字变更(表数 / 接口数 / service 数等)
- ✓ 同步了大量其他文档
- ✗ 单纯文字修正(typo / 错别字)
- ✗ 格式调整

## changelog 内容格式

每份 changelog 用**时间倒序**(最新变更在最上面),每条记录包含:

```markdown
# changelog — <原文档名>

> 跟踪该文档的所有重大变更。按时间倒序(最新的在最上面)。

---

## YYYY-MM-DD HH:MM — 简短标题

**类型**:新功能 / 修复 / 重构 / 同步

**背景**:
- 一句话说明为什么改

**改动**:
- 加了 XX 段
- 删了 XX 段
- 改了 XX 数字(从 N → M)

**触发**:
- 用户提了 XX 需求
- 发现了 XX bug

---

## YYYY-MM-DD HH:MM — 上一条变更
...
```

## 操作流程

### 修改一个文档时

1. 修改目标文档(比如 `01_数据详细设计文档.md`)
2. 检查 `修改记录/` 目录:
   - **如果 `changelog_01_数据详细设计文档.md` 已存在** → 在顶部加一条新变更记录
   - **如果不存在** → 新建 `changelog_01_数据详细设计文档.md`,文件头加"被跟踪文档"说明 + 第一条变更记录
3. 在 `changelog_01_数据详细设计文档.md` 顶部添加新条目**
4. 如果改动涉及其他文档(比如同步更新),在那些文档的 changelog 里也加条目
5. 不需要更新本 README 的清单(本 README 是说明文件,清单是临时的)

### 创建新文档时

1. 创建新文档
2. 在 `修改记录/` 下创建对应的空 `changelog_XXX.md`
3. 留待后续第一次修改时填第一条记录

### 归档"重写型"事件

如果一个文档被完全重写(几乎所有内容都变),可以在 changelog 里加一条**重大事件**记录,涵盖整个重写。例:`## 2026-09-15 09:00 — 文档全量重写(21 → 27 份)`,把这次重写当成一次变更记录。

## 模板

最小模板(用于新建 changelog):

```markdown
# changelog — <原文档相对路径>

> 被跟踪文档:`<完整路径>`
> 创建时间:YYYY-MM-DD
> 跟踪范围:重大变更(新功能 / 修复 / 重构 / 大量同步)

---

## YYYY-MM-DD HH:MM — <标题>

**类型**:新功能 / 修复 / 重构 / 同步

**背景**:
- ...

**改动**:
- ...

**触发**:
- ...
```

## 为什么是 per-文档而不是 per-事件

- **per-文档** 适合"我想知道这个文件经历过什么"
- **per-事件** 适合"我想知道 2026-09-16 那天做了什么"(这个需求用 git log 或 commit message 更合适)

我们选 per-文档,因为文档维护是项目的核心工作,需要清晰追溯每个文档的"履历"。
