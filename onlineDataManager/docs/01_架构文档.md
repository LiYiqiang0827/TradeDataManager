## §2 代码架构 — scheduler / service / core / test 四层设计

### 2.1 分层思想

**核心原则**:**单向依赖 + 职责单一**。下层不知道上层的存在:

```
┌─────────────────────────────────────────────────┐
│  scheduler 层  (3 个文件,只决定"何时跑谁")       │
│  - scheduler_onlineData.py (launchd 调度主进程) │
│  - scheduler_once.py        (一次性测试调度器)   │
│  - __init__.py                                    │
└──────────────────┬──────────────────────────────┘
                   │ spawn 子进程(subprocess)
                   ▼
┌─────────────────────────────────────────────────┐
│  service 层  (24 个文件,只决定"做什么")           │
│  - 10 个 service_writeredis_*.py (只写 Redis)    │
│  - 10 个 service_savedata_*.py (只落 SQLite)      │
│  - 2 个 service_check_*.py (检查 Redis/SQLite,v6.7 新增,**不进 plist**)|
│  - 3 个其他 service (savedata_loop 基类 + cleanredis) │
└──────────────────┬──────────────────────────────┘
                   │ 调用 core 函数
                   ▼
┌─────────────────────────────────────────────────┐
│  core 层  (10 个文件,提供所有基础能力)            │
│  - Redis / SQLite / 持久化 / 拉取 / logger       │
└─────────────────────────────────────────────────┘

   test 层独立,直接 import core + service 做验证
┌─────────────────────────────────────────────────┐
│  test 层  (24 个文件,AI 调试用)                  │
│  - 13 个 test_checkredis_*.py (check Redis,含 allkeys) │
│  - 11 个 test_checkdb_*.py    (check SQLite)     │
└─────────────────────────────────────────────────┘
```

### 2.2 scheduler 层(3 个文件)

| 文件 | 行 | 职责 |
|---|---:|---|
| `scheduler_onlineData.py` | 643 | **生产调度器**:launchd 唯一启动的入口。按当前时间阶段 spawn / kill 子 service |
| `scheduler_once.py` | 250 | **一次性测试调度器**:CLI 工具,任意时间手动跑一次全部 service,验证链路是否通 |
| `__init__.py` | — | 包标识 |

**核心设计**:
- 单一入口:launchd 只启动 `scheduler_onlineData`,**不**直接启动任何 service
- 阶段式调度:**10 个时间段**(WRITER + SAVEDATA 各 10 个,共 20 个 phase 名,见 `代码详细设计/scheduler_onlineData.md §2.1`)— v6.15 加 `idle_pre_morning`(09:26-09:29/09:30)+ `idle_pre_afternoon`(12:59-13:00)

## §3 数据架构(SQLite + Redis)

### 3.1 SQLite 月度数据库

**位置**:`~/TradingAgent/onlineDataManager/data/online_data_YYYYMM.db`(每月 1 个,例如 `online_data_202609.db`)
**模式**:WAL(Write-Ahead Logging),允许读写并发
**主键约定**:每个业务表主键 `(ts_code, trade_date)`,支持按天切片查询

**业务表清单**(**11 张**,v6.15 删 orderbook + 加 snapshot_index):

| 表名(2026-09-16 v6.15 校正)| kind | 写入脚本 | 读取脚本 |
|---|---|---|---|
| `watchlist_YYYYMMDD` | watchlist | service_writeredis_watchlist | query_db |
| `auction_YYYYMMDD` | 集合竞价 | service_savedata_auction | query_db |
| `snapshot_YYYYMMDD` | 连续竞价快照 | service_savedata_snapshot | query_db |
| `snapshot_index_YYYYMMDD` 🆕 | 8 只固定指数 | service_savedata_snapshot_index | query_db |
| ~~`orderbook_YYYYMMDD`~~ | ~~5 档盘口~~ | ~~service_savedata_orderbook~~ | ~~query_db~~ |
| `minute_YYYYMMDD` | 1 分钟分时 | service_savedata_minute | query_db |
| `zt_YYYYMMDD` | 涨停池 | service_savedata_zt | query_db |
| `break_YYYYMMDD` | 炸板池 | service_savedata_break | query_db |
| `anomaly_YYYYMMDD` | 异动 | service_savedata_anomaly | query_db |
| `hot_YYYYMMDD` | 热股榜 | service_savedata_hot | query_db |
| `limitperformance_YYYYMMDD` | 涨停表现 | service_savedata_limitperformance | query_db |
| `online_stream_cursor` | STREAM 游标持久化(跨月)| persist_client 自动维护 | query_db |

### 3.2 Redis 内存数据

**Redis 实例**:本机 Redis 6379,db 0,无密码
**命名空间**:所有业务 key 前缀 `online:`
**数据载体**:每 kind 用 1-3 种 Redis 结构(STREAM + ZSET + HSET + Window)

**Redis 表清单**(每 kind 一套):

| kind | 数据结构 | 写入脚本 | 读取脚本 |
|---|---|---|---|
| watchlist | SET + HSET | service_writeredis_watchlist | query_redis |
| auction | STREAM + ZSET + HSET(v6.2 timeline / archive) | service_writeredis_auction | query_redis |
| snapshot | STREAM + ZSET + HSET(v6.3 timeline / archive / window) | service_writeredis_snapshot | query_redis |
| snapshot_index 🆕 | STREAM + ZSET + HSET(v6.10 timeline / archive / window) | service_writeredis_snapshot_index | query_redis |
| ~~orderbook~~ | ~~STREAM + HSET + Window~~ | 🔴 v6.15 停用 | — |
| minute | STREAM + HSET | service_writeredis_minute | query_redis |
| zt / break / anomaly / hot / limitperformance | STREAM + ZSET + HSET(v6 MyATM) | service_writeredis_zt 等 | query_redis |
| meta | HSET(`online:meta`)| 各 service 写入 last_trade_date 等 | check_redis |
| cursor | HSET(`online:stream:cursor`)| persist_client 自动维护 | query_redis |

### 3.3 Redis ↔ SQLite 关系

**核心设计**:**STREAM 是桥梁**。

```
service_writeredis_X     →  Redis STREAM(XADD 追加) + ZSET(索引) + HSET(最新)
                                ↓
service_savedata_X       →  从 STREAM 读游标(last_stream_id) → 批量 INSERT SQLite
                                ↓
SQLite online_stream_cursor 表保存 last_stream_id → 重启后从上次位置继续读
```

**STREAM 游标持久化机制**:
1. savedata_X 启动时,从 `online_stream_cursor` 表读 last_stream_id
2. 用 `XREAD > last_stream_id` 拉新数据
3. 批量 INSERT 到业务表(单事务)
4. 提交后**才**更新 last_stream_id 到 `online_stream_cursor` 表
5. 失败回滚 → 游标不变 → 重试

**好处**:Redis 崩 / savedata 崩 / SQLite 锁 → 都不丢不重

| **凌晨清 Redis** | scheduler 在 `closed` 阶段触发 `service_cleanredis_online`,清空 `online:*`(**生产真值:09:00 + 03:00,2026-09-16 用户拍板默认 3 点不再回 16:00**)|

### 4.4 与下游模块的关系

```
TradingAgent/
├── offlineDataManager/  ── 历史/复权/财务(盘后跑)
├── onlineDataManager/   ── 本模块:实时行情(交易时段跑)
└── policyStudy/         ── 策略回测(消费 onlineDataManager 的 SQLite 数据)
```

**数据流**:offline + online → policyStudy。policyStudy 只读 SQLite,**不**直接读 Redis。

### §4.5 运维约定 + 跨模块接入(policyStudy 怎么读)

> 面向运维 / 监控 / 跨模块开发者。本节补 §4.4 数据流的"运维语义空白"。

#### 1. 时序约定(什么时候数据算"就绪")

| 阶段 | 时间 | writer 状态 | savedata 状态 | policyStudy 读法 |
|---|---|---|---|---|
| 连续交易 | **09:29-11:31** / **13:00-15:01**(v6.15 写入窗) | **8 个普通 daemon 跑**(snapshot/snapshot_index/minute/zt/break/anomaly/hot/limitperformance)+ auction 09:14-09:26 + watchlist 09:10 一次性 | **9 个 daemon 跑**(同上 8 个 + watchlist)| **不建议**读(中间状态)|
| 午休 | **11:31-12:59**(v6.15 lunch 窗) | 全部 kill | **11:46 进入 savedata_paused**;daemon 内部 11:31 起返回 False 不拉数据(双重保险) | 可读,但仍在消化 |
| **收盘** | **15:01-15:16**(v6.15 下午窗结束) | 15:01 全部 SIGTERM | 全部继续跑最后一次 drain(到 15:16)| **可读**,等"最后一笔落完" |
| **post_savedata 数据稳定** | **15:16 之后**(v6.15 post_savedata 窗) | — | 已全部 drain 完 | **建议读这个时间点** |

#### 2. "数据准备就绪"判断信号

policyStudy 想自动判断"今天数据已稳定可用",有两个判定方法:

- **方法 A(简单)**:等 **15:16** 之后再读(v6.15 hard-clock 约定,推荐;原 15:35 已下放至 15:16)
- **方法 B(精确)**:对比 Redis `online:<kind>:stream` 的 `XLEN` 与 SQLite `<kind>_<YYYYMMDD>` 表的 `COUNT(*)`,差值 ≤ 100(容忍 savedata 最后一轮未提交)即视为已稳定
- **方法 C(强烈不推荐)**:不等就实时读,会读到上午数据 + 下午实时数据混合,字段错乱

#### 3. 积压告警阈值(snapshot 监控样例)

`online:<kind>:stream` `XLEN` vs SQLite 表 `COUNT(*)` 差值 **> 15 分钟写入量 = 积压告警**。snapshot 写入速率约 6s/次 × 4500 股票 ≈ 750 条/分钟,15 分钟就是 **11250 条积压**:

```bash
# 监控脚本示例(挂在 cron 每分钟跑一次)
LENTMP=$(redis-cli XLEN online:snapshot:stream)
SQLTMP=$(sqlite3 ~/TradingAgent/onlineDataManager/data/online_data_$(date +%Y%m).db "SELECT COUNT(*) FROM snapshot_$(date +%Y%m%d)")
DIFF=$((LENTMP - SQLTMP))
[ $DIFF -gt 11250 ] && echo "[ALERT] snapshot 积压 $DIFF 条 (> 15 分钟)"
```

> 其他 kind 阈值按各自写入速率 × 15 分钟计算。

#### 4. policyStudy 接入约定(契约)

- **db 路径**:`~/TradingAgent/onlineDataManager/data/online_data_<YYYYMM>.db`(项目根目录下 data/)
- **表命名**:`<kind>_<YYYYMMDD>`(snapshot / orderbook / minute / zt / ...)
- **关键字段**:`lu_time`(涨停时刻 unix int64,永远保留,policyStudy 据此排序)、`data_timestamp`(数据时刻 ISO)、`created_at`(落盘时刻 ISO)
- **唯一约束**:每张业务表 `(kind, ts_code, data_timestamp)` UNIQUE,重复 INSERT 自动忽略(不报错)
- **游标持久化**:`online_stream_cursor` 表存每 kind 的 `last_id`,policyStudy **不应**改这张表(只读)

#### 5. 日志位置

- `~/TradingAgent/onlineDataManager/logs/scheduler_onlineData_YYYYMMDD.log` — 主调度器(logger.py 自动按日期切)
- `~/TradingAgent/onlineDataManager/logs/service_*_YYYYMMDD.log` — 各 service
- launchd stdout/stderr:`~/TradingAgent/onlineDataManager/logs/scheduler.launchd.{log,err.log}`(plist 配置,不是 logger.py 写)
- 重启顺序:**先 `launchctl unload` → 检查进程退出 → `launchctl load`**,不要直接 kill 进程(launchd 会立刻重启)

## §5 核心设计原则速查

| # | 原则 | 实现 |
|---|---|---|
| 1 | **写入与落盘分离** | writeredis_* 只写 Redis,savedata_* 只读 Redis 落 SQLite,完全解耦 |
| 2 | **原子化** | 一个 service 只处理一个 kind,10 个 kind × 2 角色 = 20 个独立文件 |
| 3 | **STREAM + 游标持久化** | 落盘用 Redis STREAM + SQLite `online_stream_cursor` 表,重启不丢不重 |
| 4 | **统一时间戳双时间** | 每条数据带 `data_timestamp`(数据源时间)+ `save_timestamp`(落盘时间) |
| 5 | **阶段式调度** | scheduler 按当前时间切 **10 个 WRITER + 10 个 SAVEDATA 阶段**(v6.15 加 `idle_pre_morning` / `idle_pre_afternoon`),阶段变化时 spawn/kill 对应 service |
| 6 | **单入口调度** | launchd 只启动 scheduler,service 由 scheduler 动态 spawn |
