# 实时采集完成事件与浏览器推送

- KPL performance 的正式调度参数为 `--interval 6`，每轮五个 PidType 请求并行，按开始时间到下一次开始时间计算间隔。
- 此 writer 进程的限速预算为 60 请求/分钟（目标采集量 50 请求/分钟）；其它客户端沿用现有配置。失败指数退避至最多 60 秒，不重叠启动采集轮次。任一板数失败时保留上次完整批次。
- snapshot / snapshot_index / limitperformance / zt / break 在完整数据及元信息提交后调用 OnlineRedis.emit_update；minute 在整轮完成后通知。
- `online:events` 是独立 Redis Stream，MAXLEN 约 10000，TTL 12 小时。字段 payload 为 JSON：kind、date、count、archive、codes、sourceAt、emittedAt。空池也发送 count=0 事件。消费者使用独立 XREAD 游标，不修改原有落盘游标。
- 通知失败记录 warning，不回滚已提交数据。浏览器断线重连从 API 补完整快照。
- TradingAlertSystem/limitup-dashboard/live_push.py 只运行一个阻塞读取线程，再向每个页面的一条 SSE 连接广播；行情内容取自该批完成的 archive。
- 网页路由 `/api/live-events` 使用 EventSource；`/api/live-push-status` 返回连接、事件数与最后的 Stream ID。没有浏览器定时行情轮询，15 秒服务端心跳负责连接存活与交易状态。
- 午休网页保留当日最后完整行情。5 分钟池 archive 过期后，使用同日业务 Stream 最新批次恢复，再缓存最后有效截面；显示午间快照，不引用昨天的数据。

部署：更新两仓库后，优雅重启 online scheduler，使新的 writer 加载事件发布器和 KPL 间隔。网页进程需重启以加载 live_push.py。当前采用相同 Redis 6380 配置，不新增凭据。
